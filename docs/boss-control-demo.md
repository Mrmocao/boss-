# BOSS 页面控制演示

日期：2026-10-30。范围：用户已登录的个人求职账号，按用户要求验证消息页面控制。方式：通过专用 Chrome 的 CDP 执行临时脚本。

## 实测结果

1. 根据实际页面的“消息”链接进入 `/web/geek/chat`。
2. 读取当前加载的 7 条历史会话摘要，不推断它们代表账号全部历史。
3. 打开最近一条会话，以选中行与会话页头核对对象；打开可能更新已读状态。
4. 读取当前已加载的 2 条文字消息：对方的岗位咨询，以及账号本人的后续问题。另有 1 个平台卡片，不能算作对方新回复。
5. 从实测气泡结构区分 incoming / outgoing；最后一条文字消息属于账号本人，得到 `WAITING_FOR_PEER`、`shouldReply=false`。
6. 确认输入框为空后，填入固定测试草稿：`【连接测试草稿，未发送】验证自动填写能力，稍后自动清空。`
7. 验证草稿在输入框中显示并截图；随后只清除本次测试文本。
8. 下一次读取确认输入框为空、发送按钮处于 disabled 样式、消息条目仍为 3 个（2 条文字 + 1 个平台卡片）。全过程未点击发送或按 Enter。

截图保存在 `.local/input-demo.png`，展示测试草稿当时的状态；截图不代表当前仍保留草稿。结果记录在 `.local/control-demo-result.json`。未将候选人姓名或真实聊天正文写入本公开设计记录。

## 能力边界

本次证明专用浏览器能够导航、打开会话、读取已加载文字和操作编辑器。尚未证明真实发送、发送回执、长期监听、历史翻页、稳定消息 ID 或精确去重，也不等于招聘端适配已完成。暂未把临时脚本包装成 CLI 或 MCP 聊天工具。

当前账号是求职端，消息的对方是招聘人员；公司账号作为招聘方的流程需要另行验证。

## 后续自动回复的必要判断

- 新的对方消息是否真实存在，系统卡片不能误判为对方文字。
- 当前会话、账号和回复目的是否与授权相符。
- 是否已有本账号回复、人工接管或尚未发送的用户草稿。
- 发送前是否出现新消息或会话切换。
- 发送后是否有明确回执；未知结果不能自动重试。
